# Dosette review - 18 October 2026

Scope: Android phone app, Wear OS companion, shared Data Layer protocol, backup and inventory integrity, and Google Play release preparation. Reviewed from commit `1c04907ca73bbd4c47dc6f3b3da699808d637114` on `fix/play-release-readiness`.

Implementation and local validation are complete. The signed preview and emulator upgrade results are recorded below. These checks do not certify Google Play approval or physical-device acceptance.

## Findings and changes

P1 denotes a risk to recorded doses, inventory or recovery data. P2 denotes incorrect behavior or a release-readiness gap.

| Severity | Finding / reproducible trigger | Change |
| --- | --- | --- |
| P1 | Saving a medication form after a dose or refill overwrote current stock with the value loaded when the form opened. | Serialize edits with the reminder engine, reload current medication data, and merge unchanged stock and refill timestamps in a Room transaction. Explicit quantity corrections still apply. |
| P1 | Backup export read related tables separately; changes during export could produce an inconsistent snapshot. A dose or refill between the pre-import backup and replacement could disappear from both datasets. | Read the database snapshot in one transaction. Import locks the engine and Room in that order and keeps the recovery snapshot and replacement together, including writers outside the engine mutex. |
| P1 | A settings-write failure after database replacement left a partially applied import. Repeated imports within one second overwrote the same recovery file. | A settings-write exception rolls back the database replacement. Recovery files use unique names; notification cancellation follows successful commit. |
| P1 | A watch action could be applied again after a lost acknowledgement, including after the user had undone its first application. | Store durable delivery receipts in the same database transaction as the action. Receipts cover scheduled and as-needed actions and survive undo and data replacement. Database schema 4 adds delivery receipts and per-occurrence action cursors. |
| P1 | An as-needed intake could read its old default package, then write after a concurrent backup import replaced that package. | Keep medication, schedule and variant reads in the same Room transaction as the PRN log, stock change and receipt. Import waits for the complete intake and its recovery snapshot includes it. |
| P2 | An older distinct watch action arriving after a newer skip or phone undo could overwrite the newer decision. An old cursor could also hide a restored newer mark. | Persist per-occurrence intent time with effects and receipts. Acknowledge stale or equal-time watch actions without applying them. Phone actions use decision time; restored taken/skipped marks use import time, atomically with replacement and settings-write rollback. |
| P2 | Delayed as-needed watch actions used delivery time rather than tap time. Queue order and malformed Data Layer items could also affect processing. | Preserve the intake timestamp, clamp future timestamps to receipt time, process actions in tap order, check payload/path identity, and isolate malformed items. |
| P2 | Concurrent watch reads could publish an older pending queue after acknowledgement; read errors could erase the visible snapshot. The displayed day did not advance without a phone event. | Serialize reads, preserve the last successful data, refresh time while visible, and show the snapshot date when data is stale. |
| P2 | Import accepted cross-profile dose logs, duplicate scheduled facts or time IDs, `24:00` rollover, and invalid dose/stock numbers. | Validate ownership and uniqueness, parse times strictly, and reject nonfinite, negative or otherwise invalid numeric values before writing. |
| P2 | Large cycle day counts overflowed integer addition, giving incorrect occurrence and supply calculations. | Add cycle lengths as `Long`; regression cases cover sums above `Int.MAX_VALUE`. |
| P2 | Wizard validation rejected decimal commas that saving could parse, accepted infinity, and treated invalid cycle-off text as zero. | Use consistent finite decimal parsing, validate optional inventory fields and require valid cycle integers. |
| P2 | The manifest used restricted `USE_EXACT_ALARM` on Android 13+, and onboarding did not request user-controlled exact-alarm access. | Use `SCHEDULE_EXACT_ALARM` on Android 12+, add the onboarding access card, retain the inexact fallback, and re-arm after a grant. |
| P2 | Optional background location lacked a dedicated prominent disclosure; the Android 11+ request could silently fail. Returning from permission settings did not immediately refresh waiting geofences. | Add explicit disclosure and cancellation paths, route background access through system settings, and reschedule after permission or place changes. Timed reminders remain usable without location. |
| P2 | The app lacked accessible privacy/health information, and documentation described Data Layer as Bluetooth-only. | Add an offline privacy and safety dialog, document possible Google Play services cloud transport, and prepare a public privacy-policy file and store text. |
| P2 | Existing release output was APK-only; phone and watch used the same version code. Versioned builds could fall back to debug signing. | Build APKs and AABs, allocate distinct increasing form-factor codes, require complete signing configuration for versioned builds, and verify the existing package/signing identity. |
| P2 | Release tags did not themselves establish that all quality checks and artifact compatibility checks had passed. | Add release gates and artifact checks for metadata, signatures, watch targeting, native ABI counterparts and 16 KB alignment. Preserve R8 mappings and provide a signed preview workflow. |

## Remaining limits and release gates

Room and DataStore are separate storage systems. Ordinary settings-write exceptions now roll back the database import, but a process or storage failure after DataStore succeeds and before SQLite commits can still leave settings and database contents from different generations. This change does not implement a cross-store recovery journal.

Actual phone/watch pairing, mixed Play/GitHub signatures, offline delivery and reconnection, physical location arrival, Doze behavior, reboot before first unlock, timezone/DST transitions, and installation on a 16 KB device remain acceptance checks. Unit tests and an emulator reminder do not establish reliability under every manufacturer's power policy.

The release verifier checks artifact properties; it does not replace Play bundle validation, pre-launch reports, user testing or form-factor review. The final production artifact must use the existing release identity. A debug-signed local smoke build is not a distributable release.

The owner still needs the appropriate Play developer account and verification, a real support contact, hosted privacy policy, store assets, required health/location declarations and any applicable testing period. The app can be listed as free; account registration is separate. Account eligibility and all submission decisions are detailed in the [Google Play checklist](google-play/README.md). No approval is implied by source changes.

Rollback: retain the prior source tag and a verified user export. New schema and version codes mean rollback should use a compatible forward-fix release; do not install an older database reader or downgrade a production version without a separately validated recovery procedure.
